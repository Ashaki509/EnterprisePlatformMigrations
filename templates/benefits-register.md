# Benefits Register

The benefits register records what the migration is expected to deliver and tracks whether it did. Start it during Discovery, update it at each phase gate, and keep reporting until every benefit is realized or formally closed.

## Benefit Types

| Type | Examples |
|------|----------|
| Cost reduction | Lower infrastructure cost, retired licenses, reduced support effort |
| Performance | Faster response times, higher throughput |
| Reliability | Fewer incidents, shorter recovery time |
| Security and compliance | Fewer open vulnerabilities, controls met |
| Productivity | Shorter cycle times, less manual work |
| Revenue enablement | New capabilities, faster time to market |

---

## Status Definitions

| Status | Meaning |
|--------|---------|
| Planned | Defined, and measurement has not started |
| Tracking | Being measured, on course for the target |
| At risk | Being measured, unlikely to reach the target without action |
| Realized | Target met and confirmed by the owner |
| Not realized | Target missed, with the reason recorded |
| Closed | No longer pursued, with sponsor approval |

---

## Rules for a Good Entry

- Each benefit has one owner in the business, not on the migration team. The migration delivers the capability, and the owner realizes the benefit.
- Each benefit has a baseline recorded before migration starts.
- Each measure names its data source.
- The target date accounts for the time benefits take to appear. Many arrive after stabilization.
- Costs that must stop, such as legacy licenses, are listed with the date they end.

## Review Schedule

| When | Action |
|------|--------|
| End of Discovery | Benefits defined, baselined, and assigned to owners |
| Each phase gate | Confirm the benefits are still achievable, and update the targets if scope changed |
| End of Stabilization | First measurement against targets, reported to the sponsor |
| [3, 6, and 12] months after | Follow-up measurements until each benefit is realized or closed |
